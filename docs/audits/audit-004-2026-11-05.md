# Kodingu audit 004: full project review

Date: 2026-11-05
Mode: after (session override). This is a review only; no product source was changed.
Scope: all 13 pages, light and dark, at 1280, 1024, 768, 390, and 320px; course data; editor flows; offline behavior; SEO; security headers; CI coverage; documentation.
Baseline: `docs/audits/audit-001-2026-11-01.md`, `audit-002-2026-11-01.md`, and `audit-003-2026-11-02.md`.

## Verdict

Kodingu is in good shape. The curriculum is complete, every documented solution passes its own checks, the layout audit is clean across 132 renders, the internal link graph has no broken targets, and the mobile navigation and theme switch work. The site is not ready to call delivery-clean because one challenge teaches a fact that contradicts the course data, and the check runner has no pending state during a wait that can last six seconds.

Two findings are unconditional hard gates. The 1024px touch finding is conditional on a coarse pointer, which is common on tablets but not universal. The rest is verification and performance debt, plus three low-severity documentation or keyboard notes.

## What passes

- 70 lessons: 32 HTML, 19 CSS, 19 JavaScript. Four guided projects, six extra challenges, 1,795 lesson XP, 615 practice XP, 2,410 total XP. `npm run verify` covers the solutions, tests, and totals.
- 132 renders: 0 document overflow, 0 elements outside the viewport, 0 contrast failures, 0 duplicate IDs, 0 h1 problems, 0 dead grid bands, 0 wide-text failures, and 0 focus-ring gaps.
- 44px controls at 768, 390, and 320px. Mobile navigation is 44px tall, labelled "Menu", moves focus into the panel, and returns focus to the toggle on Escape.
- Theme switch persists across reloads and follows the system preference on first visit. Reduced motion resolves to `0.00001s`.
- Course page: HTML 8 modules and 32 rows, CSS 4 and 19, JavaScript 5 and 19. An unknown course shows the empty state rather than a broken shell. All 19 JavaScript lesson links return 200.
- 15 top-level targets return 200. 88 internal links, 0 broken. No console errors or page errors in the probe.
- CSP is `script-src 'self' blob:` with no `unsafe-eval`. The harness checks the headers and the extensionless URLs. The service worker cache is `kodingu-v9`, with fonts and the current data modules in the shell.
- `sitemap.xml` URLs resolve. The reading pages are static, have server-independent content, and carry lesson JSON-LD.

### 1. HIGH: The data-table challenge teaches a wrong JavaScript lesson count

Rule: C-5 (evidence over claims), R-17 (do not present invented or stale facts as real).

Where: `assets/js/data/data-challenges.js`, challenge `extra-html-02`.

- Line 101, prompt: "JavaScript with 15".
- Line 108, requirement: "The lesson counts are 32, 19, and 15."
- Line 122, solution: `<td>15</td>`.
- Lines 154 and 157, test label and assertion: `32, 19, and 15` / `32|19|15`.

Evidence: the catalog, the home hero, `assets/js/data/course-index.js`, and `scripts/verify.mjs` expected totals all report 19 JavaScript lessons. The challenge calls these "three real course counts". The harness passes because the test compares the learner output to the same wrong number in the solution. It checks internal consistency, not truth.

Impact: a learner is asked to reproduce a false statement about the product and is told the table is correct. The error contradicts the catalog, the home page, progress totals, and the JavaScript course itself. This is the kind of content defect that a passing test suite can hide indefinitely.

Fix: change the prompt, requirement, solution, test label, and assertion to 19. Better, derive the three counts from the course data so the next curriculum change cannot make the challenge stale. At minimum, add a data check that compares the challenge's three numbers with `courses` or `getAllLessons`.

### 2. HIGH: Check has no pending state

Rule: R-27 (loading, empty, error, and success states are designed).

Where: `assets/js/editor/workspace.js`, `checkCode` at lines 138 to 155; `assets/js/editor/js-runner.js`, `TIMEOUT = 6000` at line 2.

Evidence: `checkCode` calls `beforeCheck`, then awaits `runChecks`, then calls `renderChecks`. The summary is set to "Not run" until that happens (lines 41 and 44). The Check button is not disabled and `aria-busy` is not set. The JavaScript runner has a six-second timeout, so a slow or broken script leaves the learner looking at a dead button for up to six seconds. A second click starts another run. `checkSequence` discards the stale result, but it does not prevent the duplicate wait or the duplicate work.

Impact: the interface gives no acknowledgement that a check started. On a slow lesson the learner is likely to click again, which makes the wait longer and can produce a confusing result order. The empty state and the script-error state exist; the loading state is the missing third state.

Fix: immediately set the summary to "Checking...", set `aria-busy="true"`, and disable Check (and optionally Run) before awaiting. Restore the controls in a `finally` block. Keep the existing sequence guard so an old result cannot overwrite a newer one. Add a verify case that delays the runner and asserts the pending label and disabled state.

### 3. HIGH on touch: 44px controls stop at 860px

Rule: R-03 (touch targets are at least 44 by 44px).

Where: `assets/css/app.css`.

- `.icon-button`: 40 by 40px at line 102.
- `.button-quiet`: 36px minimum height at line 166.
- `.button-small`: 36px minimum height at line 178.
- `.copy-code`: 32px minimum height at line 1188.
- The 44px overrides live inside `@media (max-width: 860px)` at lines 2660 to 2727.

Evidence: the audit reports 52 renders with compact controls, all at 1280 and 1024. At 1024 with a touch context, the lesson page has a 40px theme toggle, a 32px Copy button, and 36px Check, Run, Reset, Show hint, Show solution, and Check answer buttons. The challenge page has the same 40px and 36px controls. At 768, 390, and 320 the controls are 44px.

Audit 003 called 1024 a "pointer width". That is true for a desktop window, but not for an iPad in landscape, which is 1024 CSS pixels and has a coarse pointer. The current breakpoint assumes the latter never happens.

Impact: tablet users get targets below the stated minimum. The largest gap is Copy at 32px, which is also a small text control. Mouse users are unaffected.

Fix: apply the 44px rules at `max-width: 1024px`, or add a `@media (pointer: coarse)` branch that is independent of width. Keep 1280 compact. Add a 1024 touch render to the audit instead of treating every 1024 render as a pointer render.

### 4. MEDIUM: `npm run verify` never renders `course.html`

Where: `scripts/verify.mjs:527` to `536`; `course.html` appears only in the SEO source list at line 670. The optional `scripts/audit-ui.mjs` does render a course page, but it is not the main gate.

Evidence: `checkPages` renders index, catalog, practice, projects, progress, certificate, and 404. It does not render course. The SEO group reads the source file, so a broken import, a missing render path, or a console error in `course.js` would still pass CI. The manual probe shows the page works today: HTML 8 modules and 32 rows, CSS 4 and 19, JavaScript 5 and 19, and the unknown course empty state. That is a current-state pass, not a regression guard.

Impact: the course page is a primary route from the catalog and the source of every lesson link. A future edit to `course.js` or the course data could break it without failing `npm run verify`. `AGENTS.md` says the harness drives every page, so the documentation is broader than the harness.

Fix: add these to `checkPages`:

- `/course.html?course=html`, assert the h1 and 32 lesson rows.
- `/course.html?course=css`, assert 19 rows.
- `/course.html?course=js`, assert 19 rows.
- `/course.html?course=missing`, assert the empty state.

Also fail on any console or page error for those routes, not just on a missing h1.

### 5. MEDIUM: One lesson downloads the entire curriculum

Where: `assets/js/pages/lesson.js` imports `data.js` on line 1. `assets/js/data/data.js` imports all 12 data modules on lines 1 to 12.

Evidence from `artifacts/review/perf.mjs` against the local server:

| Page | Requests | JS requests | JS transfer | Total transfer |
| --- | ---: | ---: | ---: | ---: |
| `/lesson.html?course=html&lesson=html-01` | 30 | 22 | 478,186 B | 639,811 B |
| `/index.html` | 14 | 7 | 204,143 B | 355,408 B |

The lesson page loads every HTML, CSS, and JavaScript module, all challenge data, all project data, and all solutions. The local dev server does not compress, so production transfer will be smaller with Brotli or gzip. Compression does not remove the 22 requests, the parse work, or the fact that a single lesson needs one lesson's data.

Impact: a phone on a slow connection pays for the whole curriculum before it can show one lesson. The existing `course-index.js` split already shows the right pattern for list pages; lesson pages do not benefit from it.

Fix: generate a per-lesson data module, or a lesson index with only the selected lesson plus previous and next titles. The existing generator can do this without a build step or runtime dependency. Keep the static reading pages as they are. If this is deferred, document the current cost so it is a known choice rather than an accident.

### 6. LOW: The design system says the demo is the only shadow

Where: `DESIGN.md:47` and `DESIGN.md:89` say the hero demo carries the only shadow. `assets/css/app.css:2674` gives the open mobile navigation a `box-shadow: 0 18px 30px rgba(31, 29, 26, 0.08)`.

Evidence: the menu shadow is real and visible at mobile widths. The demo shadow is also real.

Impact: the visual decision log and the CSS disagree. The menu shadow is defensible because the panel sits above the page, but an undocumented exception weakens the "one shadow" rule. A future cleanup could remove the overlay shadow or preserve an exception that nobody recorded.

Fix: add one decision-log line: the mobile menu is an overlay and is allowed to lift; the demo is the only content surface that lifts. Or remove the menu shadow if the border is enough.

### 7. LOW: Offline does not start from a static reading page

Where: `README.md:20` says "Offline after the first visit: a service worker caches the pages, styles, and scripts." The generated reading pages load only `theme-init.js` (`scripts/make-pages.mjs:176`). `registerServiceWorker` is called from `initChrome` in `assets/js/core/app.js:885` to `889`, and the interactive page controllers call `initChrome`. `sw.js` does not list any `lessons/` page in its shell.

Evidence: a fresh browser context opened at `/lessons/html-01.html` reports `controller: false` and `registrations: 0`. The page still works online, and the reading experience is complete without JavaScript. The offline layer simply never starts on this entry path. A lesson that was never visited is also not in the shell.

Impact: a visitor who arrives from search on a reading page and never opens an interactive page has no offline cache, contrary to the README. This is a documentation and expectation gap more than a broken page.

Fix: either add a small worker registration to the generated reading pages, or narrow the README to "after visiting an interactive page" and "pages you visit are cached". If the 70 reading pages stay out of the shell, say that visited pages are cached on demand.

### 8. LOW: The skip link does not move focus

Where: `assets/css/base.css:207` defines `.skip-link`; the pages have `<main id="main">` without `tabindex`.

Evidence: activating the skip link scrolls to the main content, but `document.activeElement` remains the body. The next Tab enters the main region, so the bypass works for sequential keyboard use. It does not move focus for a screen reader or for a keyboard user who expects the target to become active.

Impact: the bypass is functional but incomplete. This is a low-severity keyboard and screen-reader polish item, not a blocker.

Fix: add `tabindex="-1"` to `main` and focus it when the skip link is activated, with a visible focus treatment that does not create a permanent outline. Keep the existing link target for no-JS and direct hash navigation.

## Engineering review

- The verification harness is stronger than the count suggests. It writes every documented solution, runs every check, answers every quiz, completes the work, and asserts the progress totals. It is the reason the wrong count in finding 1 is the only content truth defect found.
- The harness blocks service workers for the main page run and tests offline separately from the home page. That is a sensible split, but it means the static reading pages never enter the offline test.
- The CSP, extensionless URL handling, sitemap, canonical URLs, and JSON-LD are covered. The `_headers` file remains the source of truth for the browser policy.
- `sw.js` has already moved to `kodingu-v9` and includes the current font and data module names. No cache-name drift was found in this branch.
- `app.css` is large and repeats breakpoints: `860` appears twice, `720` three times, and `980` twice. This is not a current bug, but the next layout change should group the breakpoints so override order stays obvious.
- No LICENSE file was found at the project root. The README credits Reicon and the fonts, but does not state the project's own reuse terms. This is outside the UI gate; add a license before presenting the repository as reusable source.

## Limits

- Chromium only. No Safari, Firefox, iOS Safari, or physical tablet was tested. The 1024 touch result uses Playwright touch emulation at a 1024 by 768 viewport.
- The performance numbers come from the local dev server, which does not compress. They prove request count and parse weight, not production transfer size.
- Visual review sampled home at 1280 and 390. The other renders were checked by computed layout, contrast, overflow, and focus measurements, not by a human aesthetic pass.
- No screen reader was run. Keyboard focus behavior was checked directly in Chromium.
- No source files were changed. The only additions are this report and the ignored review artifacts under `artifacts/review/`.

## Recommended order

1. Fix finding 1 and add a data cross-check so the challenge cannot drift again.

3. Decide finding 3: extend the 44px rule to 1024 touch, or document why 1024 is pointer-only.
4. Add the course page to verify (finding 4).
5. Treat finding 5 as the next performance project; findings 6 to 8 are small documentation and keyboard cleanups.
